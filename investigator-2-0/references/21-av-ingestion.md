# 21. Приём аудио и видео (стенограмма и осмотр)

> Публичная редакция: частные примеры и локальные реквизиты исключены. Применяй основной SKILL.md и 27-case-workflow.md; прежние отметки «сверено», количественные ориентиры и настройки среды не подтверждают актуальность права или готовность текущего документа. Бланки подключаются локально.

Как принять аудио/видео-доказательства (записи ОРМ и «контроля и записи переговоров» по ст. 186 УПК, диктофонные записи, видео с камер, телефонные записи), сделать **черновую стенограмму** и подготовить **осмотр**. Выполняется на **Шаге 0**, до классификации жанра. Всё локально/офлайн.

## Рабочее окружение Investigator 2.0 (06.10.2026)

Обработка выполняется локально через `../run.py`. Установлены FFmpeg, WhisperX 3.8.6 и PyTorch 2.8.0 CPU. Видеокарта CUDA не обязательна. На этом компьютере проверена русская речь с моделью `base`, CPU int8 и `--no-align`; это быстрый пробный режим, его точность не переносить автоматически на сложные записи. Более крупную модель выбирать по качеству записи и доступному времени.

Проверка окружения: `python ../run.py check_env.py`. Установленные версии перечислены в `../runtime/requirements-lock.txt`. Установщиков `finish-av-setup.ps1` в комплекте нет; не ссылаться на них как на доступные.

Для обычной расшифровки токен не требуется; используется Silero VAD. Первый запуск загружает модели из интернета, запись обрабатывается на компьютере. Для повторной работы без сети нужны уже загруженные модели.

Разделение говорящих включать явно через `--diarize`. WhisperX 3.8.6 использует `pyannote/speaker-diarization-community-1`: необходимы принятые пользователем условия доступа к модели и настроенный `HF_TOKEN`. Токен не сохранять в материалах дела и не выводить в отчёт. 06.10.2026 доступ подтверждён, модель загружена: проверены русская расшифровка с одним говорящим и автоматическое выделение двух голосов на искусственной записи из четырёх реплик без задания числа говорящих. Повторные реплики получили прежние метки. Это технический тест, не оценка точности на реальных шумных записях. Назначенные метки Г1/Г2 не устанавливают личность говорящего. В текущей установке прямое декодирование файлов через TorchCodec недоступно; скрипт передаёт в WhisperX/pyannote звук в памяти, извлечённый FFmpeg.

## Алгоритм

На Windows токен можно сохранить локально через файл «Настроить доступ к модели.cmd» в корне комплекта (скрипт `../scripts/setup_hf_access.py`). Он хранится в Диспетчере учётных данных Windows; `av_ingest.py --diarize` читает его оттуда. Не отправлять токен в чат. Официальные страницы: https://huggingface.co/pyannote/speaker-diarization-community-1 и https://huggingface.co/settings/tokens . Условия доступа принимает пользователь.

При сохранении настройщик проверяет токен через Hugging Face и доступ к конфигурации модели. Повторная проверка: `python ../run.py setup_hf_access.py --verify`. Флаг `--check` подтверждает только наличие записи в Windows. Если проверка учётной записи возвращает 401, требуется исправление токена; если учётная запись доступна, а модель возвращает 401/403, проверить условия модели и права чтения. Не выводить токен или данные профиля в журнал.

1. Узнай параметры файла:
   ```
   python ../run.py av_ingest.py info "<файл>"
   ```
   (длительность, есть ли звук/видео, кодеки, дата создания).
2. **Стенограмма (расшифровка речи):**
   ```
   python ../run.py av_ingest.py transcribe "<файл>" --model base --lang ru --no-align --out "<папка проекта/расшифровка>"
   ```
   Для разделения говорящих добавь `--diarize`. Для подробного отнесения слов к говорящим используй выравнивание (без `--no-align`); оно может потребовать загрузки отдельной языковой модели. Проверенный быстрый режим `--no-align` не устанавливает принадлежность каждого слова. Если внутри невыравненного фрагмента обнаружены разные голоса, TXT/SRT отмечают необходимость сверки, вместо присвоения всего текста одному говорящему. При выровненных словах вывод разделяет реплики по смене метки. В JSON также сохраняется `speaker_turns` с обнаруженными голосовыми интервалами.

   На выходе по явно заданному пути проекта: `*.stenogramma.txt` (реплики с таймкодами и говорящими «Г1/Г2»), `*.srt` (субтитры), `*.json` (полные данные). Если число говорящих известно – добавь `--speakers N` (или `--min/--max`). Видео можно подавать напрямую – звук извлечётся сам; либо сначала `audio`.
3. **Осмотр видео:** вытащи кадры по ключевым таймкодам и опиши их:
   ```
   python ../run.py av_ingest.py frames "<видео>" 00:00:05,00:01:30,00:03:12 "<папка проекта/кадры>"
   ```
   Открой полученные JPEG, опиши, что на них, для протокола осмотра видеозаписи.
4. Прочитай/выверь стенограмму, занеси ключевое в карточку дела (`references/17-verification-checklist.md`): участники, даты, длительность, относящиеся к делу фрагменты с таймкодами.

## Привязка к процессуальным документам (через скилл)

- **Протокол осмотра и прослушивания фонограммы** (ч. 7 ст. 186 УПК) – в протоколе воспроизводится та часть фонограммы, которая относится к делу; при необходимости с участием специалиста и (или) понятых. Стенограмма из п. 2 – основа дословной части.
- **Протокол осмотра предметов (видеозаписи)** (ст. 164, 166, 177 УПК) – описание носителя и содержания записи; кадры из п. 3 – иллюстрации/ориентиры по таймкодам.
- Жанры и шаблоны – см. `references/06-genres-investigative.md` (осмотр предметов и документов).

## Рабочая аудиозапись следственного действия — источник НАПРАВЛЕНИЙ, а не текста протокола

Следователь пишет ход осмотра (обыска, выезда) на диктофон «для себя». Такая запись — **источник
версий и вопросов**, а не заготовка текста протокола. Реальный улов с 20 минут записи осмотра
05.09.2026: закопанные на участке бочки с маслом · фраза «срубили ёлки» · отсутствие порубочных
листов · перемещение автомобилей с места. Каждое — направление проверки, ни одно не попало
в протокол дословно.

**Как работать:**

1. Расшифровать (п. 2 алгоритма выше) и выписать из стенограммы **список направлений**: что
   осмотреть, что изъять, кого допросить, что истребовать. Показать список в ответе.
2. ⛔ **В ПРОТОКОЛ ИДЁТ ТОЛЬКО НАБЛЮДАЕМОЕ.** Протокол осмотра фиксирует то, что участники
   восприняли на месте (ст. 166, 180 УПК). Реплики с диктофона, оценки, догадки и версии в него
   не переносятся — они уходят в рапорт, в план и в вопросы допроса.
3. ⛔ **ТЕРМИН ИЗ ЗАПИСИ ПРОВЕРИТЬ ПО ПОДПИСАННОМУ ДОКУМЕНТУ** (правило 31 — первоисточник важнее
   пересказа): в той же сессии владелец на словах сказал «сосны», на аудиозаписи звучало «ёлки»,
   а в подписанных протоколах допросов стояли **«голубые ели»** — в документ пошло последнее.
   Предмет, порода, марка, сумма и адрес берутся из подписанного документа, а не из речи на записи.
4. Рабочая запись — не доказательство сама по себе. Нужна как доказательство — приобщать носитель
   отдельно — осмотр и прослушивание по блоку выше, жанр и шаблон в
   `references/06-genres-investigative.md`, — а не пересказывать её в протоколе осмотра места.

## Обязательные оговорки

- **ASR даёт только черновик.** Дословную стенограмму и осмотр **удостоверяет следователь** (при необходимости – специалист, понятые). Скрытые/шумные записи распознаются с ошибками – выверяй по фонограмме, особенно ФИО, числа, адреса, нецензурную/жаргонную речь.
- **Таймкоды** в стенограмме приблизительны; для протокола сверь ключевые по плееру.
- **Конфиденциальность:** обрабатывай только локально. Не загружай записи дела во внешние сервисы распознавания (Яндекс SpeechKit, Google, облачный Whisper API и т.п.).
